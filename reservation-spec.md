# Hotel Room Reservation App — Specification

> **Spec version:** 1.0  **Status:** Approved for build
> **Purpose:** This file is the single source of truth for the build. When asking Claude Code for fixes or additions, paste this spec again so the work stays anchored to it.

---

## 1. Overview

A boutique hotel needs a simple **internal** web tool for front-desk staff to manage room reservations. The hotel has a fixed inventory of three room types. The tool supports **exactly three use cases** and nothing else.

---

## 2. Scope

### 2.1 In scope — the three use cases

| # | Use case | Actor | Description | Endpoint |
|---|----------|-------|-------------|----------|
| UC-1 | **Browse availability** | Staff | View every room type and how many units are free for a chosen check-in / check-out date range. | `GET /api/availability` |
| UC-2 | **Make reservation** | Staff | Capture guest name, guest email, room type, check-in date and check-out date; the system returns a unique reservation ID. | `POST /api/reservations` |
| UC-3 | **Cancel reservation** | Staff | Remove an existing reservation by its ID. | `DELETE /api/reservations/{id}` |

A supporting read-only endpoint (`GET /api/reservations`) lists current reservations so staff can find an ID to cancel. It adds no new capability beyond the three use cases.

### 2.2 Out of scope — explicitly NOT built

| Item | Notes |
|------|-------|
| **Payment processing** | No prices, deposits, invoices, card capture or payment gateway. |
| **User authentication or login** | No users, roles, sessions, passwords or tokens. The tool is open to anyone who can reach it on the internal network. |
| **Modification of an existing reservation** | There is no edit/update endpoint (no `PUT`/`PATCH`) and no edit form. To change a booking, staff **cancel and rebook**. |
| Room photos, pricing, or descriptions | Room types have a code, a display name and a unit count — nothing else. |
| Individual room numbers / unit assignment | Inventory is tracked as a count per room type, not per physical room. |
| Email notifications, guest accounts, search, reporting | Not part of this phase. |

Any request to add an out-of-scope feature must be rejected unless this spec is updated first.

## 5. Data Model

### 5.1 `Reservation` entity

| Field | Type | Required | Rules |
|-------|------|----------|-------|
| `id` | string | system-generated | **Unique identifier** of the reservation. Format `RES-` followed by 8 uppercase hexadecimal characters, e.g. `RES-4F9A12C0`. Generated by the server; never supplied by the client. Primary key. |
| `guestName` | string | yes | Must be present and not blank after trimming whitespace. Stored trimmed. |
| `guestEmail` | string | yes | Must be present and not blank after trimming. **No format validation beyond presence.** Stored trimmed. |
| `roomType` | string (enum) | yes | One of `STANDARD`, `DELUXE`, `SUITE` (exact, uppercase). |
| `checkInDate` | string (date) | yes | ISO-8601 calendar date `YYYY-MM-DD`. Must be a real date. |
| `checkOutDate` | string (date) | yes | ISO-8601 calendar date `YYYY-MM-DD`. Must be a real date and strictly after `checkInDate`. |
| `createdAt` | string (datetime) | system-generated | ISO-8601 UTC timestamp of when the reservation was made. |

What uniquely identifies a record: **`id` only**. Two reservations may have identical guest details and dates (e.g. a guest booking two Standard rooms) and are still separate records.

### 5.2 `RoomType` entity (read-only)

| Field | Type | Notes |
|-------|------|-------|
| `code` | string | Primary key — `STANDARD` / `DELUXE` / `SUITE` |
| `name` | string | Display name |
| `totalUnits` | integer | 3 / 2 / 1 |

### 5.3 Database schema (SQLite)

```sql
CREATE TABLE room_types (
  code        TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  total_units INTEGER NOT NULL CHECK (total_units > 0)
);

CREATE TABLE reservations (
  id             TEXT PRIMARY KEY,
  guest_name     TEXT NOT NULL,
  guest_email    TEXT NOT NULL,
  room_type      TEXT NOT NULL REFERENCES room_types(code),
  check_in_date  TEXT NOT NULL,          -- YYYY-MM-DD
  check_out_date TEXT NOT NULL,          -- YYYY-MM-DD
  created_at     TEXT NOT NULL,          -- ISO-8601 UTC
  CHECK (check_in_date < check_out_date)
);

CREATE INDEX idx_reservations_type_dates
  ON reservations (room_type, check_in_date, check_out_date);
```

Cancelling a reservation **deletes** its row.

## 6. Business & Validation Rules

### 6.1 Date semantics

- A stay occupies the **nights** from `checkInDate` up to, but **not including**, `checkOutDate` (half-open interval `[checkIn, checkOut)`).
- Example: check-in `2026-12-10`, check-out `2026-12-12` occupies the nights of the 10th and 11th. Another guest may check in on the 12th.
- Two stays **overlap** when `existing.checkIn < new.checkOut` **and** `existing.checkOut > new.checkIn`.
- No restriction on past dates or maximum stay length is applied (not required by the brief).

### 6.2 Validation rules

| ID | Rule | Applies to |
|----|------|-----------|
| **VR-1** | **Check-in date must be strictly before check-out date.** Same-day or reversed dates are rejected. | `POST /api/reservations`, `GET /api/availability` |
| **VR-2** | **A room type is unavailable when all its units are already reserved for overlapping dates.** A booking is rejected if, on *any* night of the requested stay, the number of existing reservations of that room type covering that night is already equal to the room type's unit count. | `POST /api/reservations` |
| VR-3 | Guest name, guest email, room type, check-in date and check-out date are all required (non-blank). Email has no format validation beyond presence. | `POST /api/reservations` |
| VR-4 | Dates must be valid `YYYY-MM-DD` calendar dates. | `POST /api/reservations`, `GET /api/availability` |
| VR-5 | `roomType` must be one of the three inventory codes. | `POST /api/reservations` |

### 6.3 Availability calculation

For a room type and a requested range `[checkIn, checkOut)`:

```
peakReserved   = the maximum, over every night in [checkIn, checkOut),
                 of the number of reservations of that type covering that night
availableUnits = totalUnits − peakReserved      (never below 0)
```

Using the per-night peak (rather than a simple count of overlapping reservations) means back-to-back stays that never share a night do not block each other. `availableUnits` is the number of additional bookings of that type that can be made for the **whole** range.

### 6.4 Validation order for `POST /api/reservations`

Checks run in this order; the **first** failure is returned:

1. Body is valid JSON object → else `VALIDATION_ERROR`
2. VR-3 required fields → `VALIDATION_ERROR` (with `field`)
3. VR-4 date format → `VALIDATION_ERROR` (with `field`)
4. VR-5 room type → `INVALID_ROOM_TYPE`
5. **VR-1** check-in before check-out → `INVALID_DATE_RANGE`
6. **VR-2** availability → `ROOM_UNAVAILABLE`

The availability check and insert run inside a single database transaction so two simultaneous bookings cannot both take the last unit.

## 7. API

- Base path: `/api`
- Requests and responses are JSON (`Content-Type: application/json`).
- Dates are strings in `YYYY-MM-DD` form. Field names are camelCase.

### 7.1 Error response shape (all endpoints)

Every error response uses this shape:

```json
{
  "error": {
    "code": "INVALID_DATE_RANGE",
    "message": "Check-in date must be strictly before check-out date.",
    "field": "checkOutDate"
  }
}
```

| Property | Type | Notes |
|----------|------|-------|
| `error.code` | string | Machine-readable code from the catalogue in §7.6 |
| `error.message` | string | Human-readable message, safe to show in the UI |
| `error.field` | string | Optional — name of the offending request field, when one field is at fault |

---

### 7.2 UC-1 — Browse availability

**`GET /api/availability?checkIn={YYYY-MM-DD}&checkOut={YYYY-MM-DD}`**

Request: query parameters only, both required.

**Success — `200 OK`**

```json
{
  "checkIn": "2026-12-10",
  "checkOut": "2026-12-13",
  "nights": 3,
  "roomTypes": [
    { "roomType": "STANDARD", "name": "Standard", "totalUnits": 3, "availableUnits": 2, "available": true },
    { "roomType": "DELUXE",   "name": "Deluxe",   "totalUnits": 2, "availableUnits": 2, "available": true },
    { "roomType": "SUITE",    "name": "Suite",    "totalUnits": 1, "availableUnits": 0, "available": false }
  ]
}
```

`roomTypes` always contains all three types, in the order Standard, Deluxe, Suite. `available` is `availableUnits > 0`.

**Errors**

| Status | `code` | When | `field` |
|--------|--------|------|---------|
| 400 | `VALIDATION_ERROR` | `checkIn` or `checkOut` missing, or not a valid `YYYY-MM-DD` date | `checkIn` / `checkOut` |
| 400 | `INVALID_DATE_RANGE` | **VR-1 violated** — `checkIn` is not strictly before `checkOut` | `checkOut` |

Example (VR-1):

```json
{ "error": { "code": "INVALID_DATE_RANGE", "message": "Check-in date must be strictly before check-out date.", "field": "checkOut" } }
```

---

### 7.3 UC-2 — Make reservation

**`POST /api/reservations`**

Request body:

```json
{
  "guestName": "Asha Rao",
  "guestEmail": "asha@example.com",
  "roomType": "DELUXE",
  "checkInDate": "2026-12-10",
  "checkOutDate": "2026-12-13"
}
```

**Success — `201 Created`**

```json
{
  "reservation": {
    "id": "RES-4F9A12C0",
    "guestName": "Asha Rao",
    "guestEmail": "asha@example.com",
    "roomType": "DELUXE",
    "checkInDate": "2026-12-10",
    "checkOutDate": "2026-12-13",
    "createdAt": "2026-11-26T11:43:00.000Z"
  }
}
```

**Errors**

| Status | `code` | When | `field` |
|--------|--------|------|---------|
| 400 | `VALIDATION_ERROR` | Body is not a JSON object; a required field is missing or blank; a date is not a valid `YYYY-MM-DD` | the offending field (absent for a bad body) |
| 400 | `INVALID_ROOM_TYPE` | `roomType` is not `STANDARD`, `DELUXE` or `SUITE` | `roomType` |
| 400 | `INVALID_DATE_RANGE` | **VR-1 violated** — `checkInDate` is not strictly before `checkOutDate` | `checkOutDate` |
| 409 | `ROOM_UNAVAILABLE` | **VR-2 violated** — every unit of the room type is already reserved on at least one night of the requested stay | `roomType` |

Example (VR-1 violated):

```json
{ "error": { "code": "INVALID_DATE_RANGE", "message": "Check-in date must be strictly before check-out date.", "field": "checkOutDate" } }
```

Example (VR-2 violated):

```json
{ "error": { "code": "ROOM_UNAVAILABLE", "message": "No Suite rooms are available from 2026-12-10 to 2026-12-13. All 1 unit(s) are already reserved for overlapping dates.", "field": "roomType" } }
```

Example (missing field):

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "guestEmail is required.", "field": "guestEmail" } }
```

No reservation is created when any error is returned.

---

### 7.4 UC-3 — Cancel reservation

**`DELETE /api/reservations/{id}`**

Request: path parameter `id` (e.g. `RES-4F9A12C0`); no body.

**Success — `200 OK`**

```json
{ "id": "RES-4F9A12C0", "message": "Reservation RES-4F9A12C0 has been cancelled." }
```

The reservation row is deleted and its unit becomes available again immediately.

**Errors**

| Status | `code` | When |
|--------|--------|------|
| 404 | `RESERVATION_NOT_FOUND` | No reservation exists with that ID (including one that was already cancelled) |

```json
{ "error": { "code": "RESERVATION_NOT_FOUND", "message": "Reservation RES-00000000 was not found." } }
```

---

### 7.5 Supporting — List reservations

**`GET /api/reservations`** — no parameters.

**Success — `200 OK`**

```json
{
  "reservations": [
    {
      "id": "RES-4F9A12C0",
      "guestName": "Asha Rao",
      "guestEmail": "asha@example.com",
      "roomType": "DELUXE",
      "checkInDate": "2026-12-10",
      "checkOutDate": "2026-12-13",
      "createdAt": "2026-11-26T11:43:00.000Z"
    }
  ]
}
```

Sorted by `checkInDate`, then `createdAt`. Empty list when there are none. No error cases beyond `500`.

### 7.6 Error code catalogue

| `code` | HTTP status | Meaning |
|--------|-------------|---------|
| `VALIDATION_ERROR` | 400 | Missing/blank field, malformed date, or malformed JSON body |
| `INVALID_ROOM_TYPE` | 400 | Unknown room type code |
| `INVALID_DATE_RANGE` | 400 | **VR-1** — check-in not strictly before check-out |
| `ROOM_UNAVAILABLE` | 409 | **VR-2** — all units of the room type reserved for overlapping dates |
| `RESERVATION_NOT_FOUND` | 404 | Cancel requested for an unknown ID |
| `NOT_FOUND` | 404 | Unknown `/api` route |
| `INTERNAL_ERROR` | 500 | Unexpected server failure (message is generic) |

## 8. Frontend

A single page (React) with three panels, one per use case. No routing, no login screen.

| Panel | Inputs | Calls | Shows |
|-------|--------|-------|-------|
| **1. Browse availability** | Check-in date, check-out date, *Check availability* button | `GET /api/availability` | A table: Room type · Total units · Available units · status badge (Available / Fully booked) |
| **2. Make reservation** | Guest name, guest email, room type (dropdown of 3 types), check-in date, check-out date, *Reserve* button | `POST /api/reservations` | On success, a confirmation with the **reservation ID**. On error, the `error.message` from the API next to the form. |
| **3. Cancel reservation** | Reservation ID text box, *Cancel* button; plus a list of current reservations each with its own *Cancel* button | `DELETE /api/reservations/{id}`, `GET /api/reservations` | Success message, or `error.message` for unknown IDs |

Behaviour:

- The frontend does not duplicate business rules; the API is authoritative and its `error.message` is shown to the user verbatim.
- The frontend may use HTML `required` attributes and `type="date"` inputs for convenience.
- After a successful reservation or cancellation, the availability table (if shown) and the reservation list refresh.
- No edit button exists anywhere (modification is out of scope).

## 10. Running the App

Prerequisite: Node.js 20+ and npm.

```bash
npm run setup     # installs server and client dependencies
npm start         # builds the React app, then starts the server
# open http://localhost:3001
```

Development (hot reload, two terminals):

```bash
npm run dev:server   # API on http://localhost:3001
npm run dev:client   # UI on http://localhost:5173 (proxies /api to 3001)
```

Tests:

```bash
npm test
```

## 11. Acceptance Criteria

| ID | Given / When / Then |
|----|---------------------|
| AC-1 | Given an empty database, when availability is requested for any valid range, then Standard shows 3, Deluxe 2 and Suite 1 available units. |
| AC-2 | When a valid reservation is posted, then the API returns `201` with a reservation whose `id` matches `RES-[0-9A-F]{8}`, and the room type's available count for overlapping dates drops by one. |
| AC-3 | When a reservation is posted with `checkInDate` equal to or after `checkOutDate`, then the API returns `400 INVALID_DATE_RANGE` and nothing is stored. **(VR-1)** |
| AC-4 | Given the single Suite is booked 10–13 Dec, when another Suite booking for 12–14 Dec is posted, then the API returns `409 ROOM_UNAVAILABLE`. **(VR-2)** |
| AC-5 | Given the Suite is booked 10–13 Dec, when a Suite booking for 13–15 Dec is posted, then it succeeds (check-out day is free). |
| AC-6 | When a reservation is posted without `guestEmail`, then the API returns `400 VALIDATION_ERROR` with `field: "guestEmail"`. Any non-blank email string (e.g. `"abc"`) is accepted. |
| AC-7 | When an existing reservation is deleted by ID, then the API returns `200`, and the unit becomes available again for those dates. |
| AC-8 | When a delete is requested for an unknown ID, then the API returns `404 RESERVATION_NOT_FOUND`. |
| AC-9 | No endpoint exists for payment, login or modifying a reservation (`PUT`/`PATCH /api/reservations/{id}` return `404 NOT_FOUND`). |
| AC-10 | Following §10, the app starts and the three panels work in the browser. |
